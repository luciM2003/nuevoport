How I work

How a project moves from question to release.

Six stages, each with a piece of a real deliverable.

  1. 01

    Discover

    I look at what people already use: tools, spreadsheets, messages. The output is a list of questions ranked by how much they block.

    1. Is delivery paid in cash or digitally?
    2. Which documents does a rider need?
    3. What happens to a canceled order?
    MODO YA, client questions

  2. 02

    Define

    I reduce findings to one problem, the roles involved and the rules that can’t break. What each person must not see counts as much as what they see.

    Access per role
    SeeEdit
    QualityAllOperations
    SalespersonOwnOwn
    ManagementAllNone
    BYD, roles and permissions

  3. 03

    Design

    Structure before style: flow, states and exceptions first, then interface and tokens. Each step asks for a single decision.

    1. Day
    2. Slot
    3. Extras
    4. Deposit
    • 11:00
    • 12:30
    • 09:30
    Padel Hub, booking flow

  4. 04

    Validate

    I review against heuristics, tasks and the real system, and rate each finding by severity. What isn’t tested is written down as open.

    • 3
    • 2
    • 1

    Severity. 6 issues found, 5 fixed, 1 open

    Turno, heuristic evaluation

  5. 05

    Deliver

    I agree components, permissions and edge cases with whoever builds them, and often build them myself. Design QA happens on the running product.

    • primary-container
    • primary
    • surface
    Padel Hub, tokens in code

  6. 06

    Iterate

    Small releases, each one closing something. I prefer knowing what is missing to announcing that it is finished.

    15 builds, September to October 2026

    MODO YA, releases

Decision

The button is visible but clearly unavailable, and the hint says what is missing.

In code

<Button disabled={code.length < 4}>

Decision

This was the finding: with one to three digits the button looked active and did nothing. Now the hint counts what is left.

In code

hint = t('digitsLeft', { n: 4 - code.length })

Decision

Only here does the action become primary. One decision per screen.

In code

status = code.length === 4 ? 'ready' : 'incomplete'

Decision

The field locks, so the same delivery can’t be confirmed twice.

In code

<input readOnly={status === 'checking'} />

Decision

It says what happened and what to do next. The digits stay, so they can be corrected.

In code

<input aria-invalid aria-describedby="hint" />

Decision

A second finding: with no network, a panel showed zeros and a green banner. An unknown result is never shown as a success.

In code

catch { setStatus(navigator.onLine ? 'wrong' : 'offline') }

About

I came to design through product.

Languages
Spanish (native), English (intermediate)
Location
Mendoza, Argentina (UTC−3)
Looking for
Senior UX/UI, Product Designer or Design Engineer roles

I started in 2022 as a freelance product manager: gathering requirements, ordering priorities and keeping clients and developers talking about the same thing. In 2023 I moved into UX/UI and front-end, to decide not only what gets built but how it works.

I approach a problem by looking at how people already work. In the BYD portal that meant keeping the spreadsheets the team trusted. In MODO YA, letting restaurants keep selling on WhatsApp. Several times the best decision was to change less.

I like products that have to work every day for people who didn’t choose them: a quality team, whoever runs a club, a rider between two deliveries. I enjoy sitting with the different areas involved, agreeing on the rules and then seeing the interface hold up.

I work from Mendoza, Argentina, and I’m looking for a product team, remote and international, where design takes part in deciding what to build.
